# AES (Advanced Encryption Standard) — deep dive

[← Guide index](../README.md) · Overview: [plain-language version](../techniques/aes.md) · Crate: [aes](../crates/aes.md) · Security: [defense.md § AES](../../defense.md#aes)

## The idea

AES is the world's standard symmetric block cipher (FIPS 197, 2001). It takes a **16-byte
block** and a key of 16, 24 or 32 bytes (AES-128, AES-192, AES-256) and scrambles the block
through 10, 12 or 14 **rounds**. Each round mixes the bytes so thoroughly that after two rounds
every output bit depends on every input bit, and only someone with the key can undo it.

Before reading on, you should know that in AES, bytes are elements of the field GF(2^8):
adding is XOR and multiplying uses `xtime` ([math primer § 5](../math-primer.md#gf28-bytes-as-polynomials-aes)).

## Theory

### The state

The 16-byte block is arranged as a 4×4 matrix of bytes, **filled column by column**:

```
bytes:  b0 b1 b2 ... b15

state:  b0  b4  b8  b12      row 0
        b1  b5  b9  b13      row 1
        b2  b6  b10 b14      row 2
        b3  b7  b11 b15      row 3
```

In the code the state stays a flat `[u8; 16]` and byte `(row, column)` is `state[column * 4 + row]`.

### The round structure

```
AddRoundKey(round key 0)
repeat rounds − 1 times:
    SubBytes      — non-linear byte substitution (confusion)
    ShiftRows     — rotate rows (diffusion across columns)
    MixColumns    — mix each column (diffusion inside a column)
    AddRoundKey   — XOR the round key
last round: SubBytes, ShiftRows, AddRoundKey   (no MixColumns)
```

Each step is invertible; deciphering runs the inverse steps in reverse order.

#### SubBytes: the S-box

Each byte `x` is replaced by `S(x)`:

1. Take its inverse in GF(2^8): `y = x⁻¹` (with `0 ↦ 0`).
2. Apply a fixed affine map: `S(x) = y ⊕ rotl(y,1) ⊕ rotl(y,2) ⊕ rotl(y,3) ⊕ rotl(y,4) ⊕ 0x63`.

The inversion is the only non-linear part of AES: without it, AES would be a big system of
linear equations, solvable directly. Example: `S(0x00) = 0x63`, `S(0x53) = 0xed`.

#### ShiftRows

Row `r` rotates left by `r` positions. Row 0 stays, row 1 moves by one, and so on. After it,
each column holds bytes coming from four different columns.

#### MixColumns

Each column `(a, b, c, d)` is multiplied by a fixed matrix over GF(2^8):

```
| 2 3 1 1 |   | a |
| 1 2 3 1 | × | b |      e.g. a' = 2·a ⊕ 3·b ⊕ c ⊕ d
| 1 1 2 3 |   | c |
| 3 1 1 2 |   | d |
```

Changing one input byte changes all four output bytes. With ShiftRows, two rounds spread every
byte everywhere.

#### AddRoundKey

XOR the state with the 16-byte round key of this round.

### Key expansion

The key is expanded into `rounds + 1` round keys (176 bytes for AES-128). It is viewed as
`Nk` 4-byte words (`Nk` = 4, 6 or 8). Each new word `w[i]` is:

```
temp = w[i−1]
if i mod Nk == 0:   temp = SubWord(RotWord(temp)) ⊕ (Rcon, 0, 0, 0)
elif Nk == 8 and i mod 8 == 4:   temp = SubWord(temp)          (AES-256 only)
w[i] = w[i−Nk] ⊕ temp
```

- `RotWord` rotates the 4 bytes by one: `[a, b, c, d] → [b, c, d, a]`.
- `SubWord` applies the S-box to each byte.
- `Rcon` is the round constant `1, 2, 4, 8, 16, 32, 64, 128, 0x1b, 0x36`: successive
  `xtime`s of 1. It makes every round key different even for a symmetric key.

### Modes: ECB and CTR

AES alone ciphers exactly 16 bytes. A *mode* handles longer messages:

- **ECB** (`my_pgp aes` stream mode, as the subject asks): pad with zeros to a multiple of 16,
  cipher every block independently. Simple but leaks patterns
  ([defense.md](../../defense.md#aes)).
- **CTR** (used inside the [X25519 mode](x25519.md#hybrid-encryption-ecies-like)): cipher a
  counter `nonce, nonce+1, …` and XOR the result with the message, like a one-time pad
  generated by AES. No padding, and identical blocks give different output.

### Byte order in my_pgp

The subject gives keys and ciphertexts as little-endian hex numbers, *per 32-bit word*. The
function `reverse_words` reverses each group of 4 bytes to convert between that convention
and the byte order of the AES state. It is applied to the key, to the ciphertext before
deciphering, and to the output after ciphering (not to the plaintext).

```
$ echo 'All men must die' | ./my_pgp aes -c -b 57696e74657220697320636f6d696e67
744ce22c385958348f0df26eceb62eef
```

### Building a key

```rust
pub fn get_aes_key(key: Bytes) -> Result<Self> {
    let rounds = key_expansion::round_count(key.len())?;   // 16→10, 24→12, 32→14
    let round_keys = key_expansion::expand(&key, rounds)?;
    Ok(Self { round_keys })
}
```

`expand` follows the key-expansion pseudocode literally. `Rcon` is not a table: it starts at
`1` and becomes `field::xtime(rcon)` after each use. The words are then regrouped into 16-byte
round keys.

### One block

```rust
pub fn cipher(state: &mut State, round_keys: &[[u8; 16]]) {
    let round_count = round_keys.len() - 1;
    add_round_key(state, &round_keys[0]);
    for round_key in &round_keys[1..round_count] {
        substitute_bytes(state);
        shift_rows(state);
        mix_columns(state);
        add_round_key(state, round_key);
    }
    substitute_bytes(state);
    shift_rows(state);
    add_round_key(state, &round_keys[round_count]);
}
```

`decipher` mirrors it: last round key first, then `inverse_shift_rows`,
`inverse_substitute_bytes`, `add_round_key`, `inverse_mix_columns` per round.

`shift_rows` copies the state and reads `previous[((column + row) % 4) * 4 + row]`: the byte
`row` positions further right in the same row.

### Stream mode (ECB)

```rust
fn cipher(&self, plaintext: &Bytes) -> Result<Bytes> {
    let mut padded = plaintext.to_vec();
    let padding = (16 - padded.len() % 16) % 16;
    padded.resize(padded.len() + padding, 0);
    for block in padded.as_chunks_mut::<16>().0 {
        rounds::cipher(block, &self.round_keys);   // each block on its own: ECB
    }
    Ok(Bytes::new(padded))
}
```

`decipher` checks the length is a multiple of 16, deciphers each block in place, and strips
trailing zeros.

## Optimisations

### Key expansion

The key is expanded once in `Aes::get_aes_key`, and the round keys are stored in the struct.
Ciphering a 1 MiB message runs 65 536 blocks with the same precomputed round keys.

### MixColumns with one `xtime` per byte

The textbook formula `a' = 2·a ⊕ 3·b ⊕ c ⊕ d` needs a `·3`, which is `·2 ⊕ ·1`. Rewrite it:

```
a' = 2a ⊕ 3b ⊕ c ⊕ d
   = 2a ⊕ 2b ⊕ b ⊕ c ⊕ d
   = a ⊕ (a ⊕ b ⊕ c ⊕ d) ⊕ 2(a ⊕ b)
```

The sum `all = a ⊕ b ⊕ c ⊕ d` is shared by the four outputs, so a column costs 4 `xtime`s and a
few XORs:

```rust
let all = a ^ b ^ c ^ d;
column[0] = a ^ all ^ field::xtime(a ^ b);
column[1] = b ^ all ^ field::xtime(b ^ c);
column[2] = c ^ all ^ field::xtime(c ^ d);
column[3] = d ^ all ^ field::xtime(d ^ a);
```

### InvMixColumns reusing MixColumns

The inverse matrix uses the coefficients `14, 11, 13, 9`, which would need many `xtime`s per
byte. The book *The Design of Rijndael* (§4.1.3) shows that the inverse polynomial factors as
the forward one times `{04}x² + {05}`. So the code first applies that cheap factor, then the
forward MixColumns:

```rust
let even = field::xtime(field::xtime(a ^ c));   // 4·(a ⊕ c)
let odd  = field::xtime(field::xtime(b ^ d));   // 4·(b ⊕ d)
*column = [a ^ even, b ^ odd, c ^ even, d ^ odd];
// then mix_columns(state)
```

4 extra `xtime`s per column instead of a full multiplication by `9, 11, 13, 14`.

### Bitsliced S-box

The classic implementation of SubBytes is a 256-byte lookup table. It is fast but **leaks the
key through the CPU cache** (Bernstein's 2005 attack): the table index is `plaintext ⊕ key`,
and which cache line was loaded can be measured.

This project computes the S-box with logic gates instead, on all 16 bytes at once:

1. **Transpose to bit planes** (`to_planes`). `planes[b]` is a 16-bit integer holding bit `b`
   of each of the 16 bytes. The transpose of each 8-byte half is an 8×8 bit-matrix transpose
   done with three mask-and-shift steps (`transpose8`, from *Hacker's Delight* §7-3):

   ```rust
   let t = (x ^ (x >> 7)) & 0x00aa_00aa_00aa_00aa;  x ^= t ^ (t << 7);   // swap 1×1 blocks
   let t = (x ^ (x >> 14)) & 0x0000_cccc_0000_cccc; x ^= t ^ (t << 14);  // swap 2×2 blocks
   let t = (x ^ (x >> 28)) & 0x0000_0000_f0f0_f0f0; x ^ t ^ (t << 28)    // swap 4×4 blocks
   ```

2. **Run the circuit** (`circuit`). Boyar and Peralta (2012) found a circuit computing the
   whole S-box with **32 AND and 96 XOR/XNOR gates**: a linear layer, the GF(2^8) inversion
   done in a "tower field" (GF(2^8) seen as GF((2^4)^2), where inverting is cheap), and a
   linear output layer that includes the affine map. Each gate is one operation on a `u16`,
   so it processes **16 bytes in parallel** (one per bit of the `u16`).

3. **Transpose back** (`from_planes`).

Result: no table, no branch, no memory access that depends on the data. The alternative
constant-time approach, reading all 256 table entries under a mask for each of the 16 bytes,
would cost thousands of operations per block; the circuit costs 128 gates plus the transposes.

### Inverse S-box from the forward circuit

The inverse S-box would need its own circuit. Instead, the code uses an identity. Let
`g(x) = A⁻¹(x ⊕ 0x63)` undo the affine step (`A⁻¹` is `rotl 1 ⊕ rotl 3 ⊕ rotl 6`, and the
`0x05` constant comes from `A⁻¹(0x63)`). Then:

```
S(y) = A(y⁻¹) ⊕ 0x63   ⇒   g(S(y)) = y⁻¹
S⁻¹(x) = g(x)⁻¹ = g(S(g(x)))
```

So `inverse_substitute` is `inverse_affine`, the forward `circuit`, then `inverse_affine`
again: cheap linear steps around the circuit that already exists. On bit planes, a rotation is
just picking a different plane, so `inverse_affine` is 3 XORs per plane plus two NOTs.

## Constant time

- SubBytes is the bitsliced circuit above (no table).
- `field::multiply` (used by the key schedule's one-byte S-box) always runs its 8 steps and
  selects with a mask instead of `if`:

  ```rust
  for bit in 0..8 {
      result ^= left & mask((right >> bit) & 1);   // mask = 0x00 or 0xff
      left = xtime(left);
  }
  ```

- `xtime` itself is branch-free: `(value << 1) ^ (0x1b & mask(value >> 7))`.
- `inverse(x)` is `x^254` by square-and-multiply; it branches only on the public constant 254.

`cargo run --release --bin timing` checks `aes-128-key` and `aes-128-plaintext` for leaks
([constant-time-audit.md](../../constant-time-audit.md)).
